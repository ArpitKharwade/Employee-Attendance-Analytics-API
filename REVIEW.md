# REVIEW.md

Review of the starter `app/main.py`. Line numbers refer to the **starter** file. Every example marked "ran it" was
executed against the starter's helper functions; the endpoint defects were found by reading the code against
`openapi.yaml` (there is no MongoDB in my sandbox, see README).

| # | Where (function / line) | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (33-37) | Works on a naive datetime and builds the shift start on *that datetime's own date, in the same naive zone*. Punch times come from epoch ms / MongoDB as UTC, shifts are IST, so every comparison is off by 5h30m. | Ran it: punch-in 09:45 IST (04:15 UTC) on a 09:30 shift gives 0, should be 15. | Convert to IST, build the shift start from the record's attendance date at `shift_start` in IST (`_ist_at`). |
| 2 | same (36-37) | Grace rule is wrong. `int(seconds / 60)` floors first, then `> 10`, so 09:40:01 up to 09:40:59 count as 10 minutes and are *not* late. R2 says late when strictly more than 10:00. | Ran it: 09:40:01 and 09:40:30 return 0, should be 10. | Compare in **seconds** (`secs > 600`), then `secs // 60`. Instants are truncated to whole seconds first (R1). |
| 3 | same | Ignores overnight shifts: the start is always on the punch-in's calendar day. A 02:00 punch-in on a 22:00 shift is "before" its shift start and returns 0 instead of 240. | Ran it: returns 0. | The start is on the *attendance date* (R1), which for an overnight shift is the previous day. |
| 4 | `compute_work_hours` (40-41) | `round()` is banker's rounding on a binary float (R4 wants half-up), and punch times are not truncated to seconds. | Ran it: 9h07m30s gives 9.12 (should be 9.13); 2h40m30s gives 2.67 (should be 2.68). | Truncate to seconds, `Decimal(secs) / Decimal(3600)`, `ROUND_HALF_UP`. One `half_up()` helper is used for every reported number (R8). |
| 5 | `compute_overtime` (44-47) | (a) Missing the 30-minute minimum (R3): 10 minutes late-out counts as 10. (b) Shift end is always on the record's date, so an overnight shift's overtime is a day too large. (c) Subtracts an aware IST value from whatever `punch_out` is; with PyMongo's naive datetimes this raises `TypeError` (500). | Ran it: 18:40 out gives 10 (should be 0); overnight 06:40 out gives 1480 (should be 40); naive `punch_out` raises. | `mins >= 30` else 0, shift end +1 day when `shift_end <= shift_start`, everything aware (see #6). |
| 6 | module level `MongoClient(...)` (23) | Not `tz_aware`, so PyMongo returns naive datetimes and each conversion is a guess. | Any code that mixes a stored datetime with an aware one raises `TypeError`; epoch conversion silently uses the server's local zone. | `MongoClient(..., tz_aware=True)`; `dt_to_ms` / `ms_to_dt` are the only conversion points. |
| 7 | `create_employee` (77-85) | Check-then-insert race: two concurrent creates both pass `find_one` and both insert; there is no unique index at all. | Fire two identical POSTs in parallel: two 201 and two documents. | Unique index on `emp_code`; `insert_one` and catch `DuplicateKeyError` -> 409. |
| 8 | `EmployeeIn` (52-59) and `create_employee` | No validation: any `emp_code` format, any email, `"25:99"` shift times, `shift_start == shift_end`, impossible `joined_on`, empty names. Must be 422. | `POST` with `shift_start: "25:99"` returns 201. | Pydantic constraints from the contract, a real-date check for `joined_on`, and a model validator for `shift_start != shift_end`. |
| 9 | `create_employee` (82, 85) | `datetime.now()` is naive server-local time, not UTC. The response returns a `datetime` (ISO string) instead of epoch ms, and `created_at` could be sent by a client. | Response `created_at` is `"2026-07-06T10:00:00"`. | UTC-aware `now_utc()`, response converted to epoch ms, client value never read. |
| 10 | `list_employees` (89-96) | (a) `skip = page * page_size` skips the whole first page (page 1 is really page 2). (b) `total` counts all employees, ignoring `department`. (c) No sort, so pages are not stable; contract says `emp_code` ascending. (d) `page=0`, `page_size=-1` or `1000000` are accepted. (e) `created_at` returned as datetime. | `GET /employees?page=1` skips the first 20 rows; `?department=X` shows the total of the whole company. | `skip = (page-1) * page_size`, `count_documents(q)`, `.sort("emp_code")` backed by a `(department, emp_code)` index, `Query(ge=1)` / `le=100` (R10). |
| 11 | `punch_in` (100-121) | Unknown employee: `emp` is `None`, then `emp["shift_start"]` raises `TypeError` -> 500 instead of 404. | `POST /attendance/punch-in {"emp_code": "EMP9999"}` | 404 before anything else. |
| 12 | `punch_in` (102) | `datetime.fromtimestamp(ms / 1000)` uses the **server's local zone**, so the stored instant and `date` depend on where the code runs. The date is also not the IST date or the overnight attendance date (R1). `if body.punched_at` treats `0` as "missing"; seconds-looking values (1783312500) are silently accepted as a 1970 date; huge values raise `OverflowError` (500). The timestamp is not truncated to seconds. | Run the service on a UTC machine and punch in at 00:30 IST: `date` is the previous day. | `EpochMillis` type (strict int, 1e11 <= v <= 4.1e12, else 422), `ms_to_dt` is UTC and truncates, `attendance_date()` implements R1. |
| 13 | `punch_in` (104-118) | Check-then-insert race again: two parallel requests both see "no record" and both insert, giving two records for one day. | Two parallel identical punch-ins return two 201s. | Unique index `(emp_code, date)`; one insert wins, the loser's `DuplicateKeyError` becomes 409. |
| 14 | `PunchInIn.status` (66) and `punch_in` | `status: str` accepts anything, including `ABSENT`, `LEAVE` and `"banana"`. Only `PRESENT`/`WFH`/`ON_DUTY` may be created by punch-in. | `{"status": "ABSENT", ...}` returns 201 with a punch time on an ABSENT record. | `Literal["PRESENT", "WFH", "ON_DUTY"]`. |
| 15 | `punch_in` response (118-121) | Leaks `id` (the ObjectId as a string, which the contract forbids), returns datetimes instead of epoch ms, and the derived fields are not computed through one shared function. | The 201 body has `"id": "65f..."` and ISO strings. | `attendance_out()` builds the response from an allow-list of fields, epoch ms for instants; derived fields come from `derive()` shared with punch-out and PATCH. |
| 16 | `list_attendance` (125-150) | Loads **every matching document** into memory, sorts and slices in Python: slow and memory-hungry at 100k records. Sort is `date` only (no `emp_code` tie-break), so order is arbitrary. `total` is `len(docs)`. `page=0` gives negative slice indices. `date_from > date_to` is not rejected, dates and `status` are not validated, and `_id` leaks as `id`. Legacy documents without `history` / `half_day` are returned without them. | `GET /attendance?page=0` returns a wrong slice; large data is slow; `?date_from=garbage` returns 200. | Database-side `find().sort(date desc, emp_code asc).skip().limit()`, `count_documents` for the total, validated dates and status, defaults filled in `attendance_out()`, and three indexes that serve every filter combination. |
| 17 | `/health` (72-74) | Always returns `ok`, even if MongoDB is down. The contract wants 503. | Stop MongoDB: `/health` still says 200, the runner starts testing a dead service. | `db.command("ping")`; any `PyMongoError` -> 503. |
| 18 | whole file | No indexes at all, so the "fast at 100k" requirements fail and `explain` would show `COLLSCAN`. | `explain()` on any list query. | `ensure_indexes()` at startup (idempotent), listed in DECISIONS.md. |
| 19 | whole file | Endpoints left as TODO: punch-out, PATCH, the analytics and explain endpoints. | Contract tests. | Implemented (Part B/C). |

## Looked at and decided it is not a defect

* `load_dotenv()` at import: by default it does **not** override variables that are already set, so real environment
  variables win, as required.
* `IST = timezone(timedelta(hours=5, minutes=30))`: correct, India has no DST. I kept it.
* `doc.pop("_id", None)` after `insert_one` in `create_employee`: `insert_one` adds `_id` to the dict, so removing it is
  right (the new code builds the response from an allow-list instead).
* `find(q, {"_id": 0})` projection and building `q` from optional filters: fine.
* The module-level `MongoClient`: PyMongo connects lazily and the client is thread-safe, so sharing one is correct.
* Sync (`def`) endpoints: FastAPI runs them in a thread pool and PyMongo is blocking, so this is the right pairing
  (an `async def` calling PyMongo would block the event loop).
